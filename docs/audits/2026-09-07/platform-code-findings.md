## Immediate priorities

1. **P1 — Public reviews leak the order UUID used as payment-page authority.** `supabase/migrations/20260722090000_init.sql:25–30` enables public SELECT on every column of published reviews; `20260805100000_lifecycle_marketing.sql:29–34` adds `order_id` to that same table. No later column restriction found. `/pay/[id]` queries service role using only UUID (`app/(store)/pay/[id]/page.tsx:41–61`) and renders purchase items/amount, plus email later in page. This is independent of the sequential thank-you exposure found by frontend audit. Order numbers are explicitly sequential (`20260724110000_commerce.sql:136–140`). Treat as schema-level exposure contingent on these grants being deployed, not proof live customer records were accessed. Replace bearer order PKs with independent signed/scope-limited receipt/payment tokens; expose reviews through a public projection or explicit column grants that exclude internal order references. Validate with synthetic orders/reviews on isolated DB: anon cannot select order_id, published review cannot unlock receipt, wrong/missing/tampered/expired tokens fail, legitimate customer link works. Effort 1–3 days, coordinated frontend/database fix.

2. **P1 — Checkout creation is not an atomic transaction and has no submission idempotency.** `lib/admin/orders.ts:157–163` reserves each line through separate RPC calls, :188–205 inserts order, :236–237 inserts items. The :253–256 catch releases reservations only; an inserted pending order is left behind if items fail, and process termination can bypass compensations altogether. `app/(store)/checkout/actions.ts:169–198` writes payment reference/expiry *after* create returns; a failure here returns a generic checkout error (:231–242), leaving the order/reservation live but encouraging shopper retry. `PlaceOrderInput` (:40–49) and orders DDL have no idempotency key. Payment expiry sweep ignores rows with null expiry (`lib/admin/payment-ops.ts:203–209`). Move order, items, pool reservations, payment plan and outbox enqueue into one DB transaction; unique checkout-attempt key returns the existing result on retry. Validate concurrent identical submits and injected failure at each stage: exactly one complete order or no order/reservation; no null-expiry pending orders. Effort 4–7 days with transition work.

3. **P1 — Order state flags do not protect concurrent/retried stock movements.** `lib/admin/orders.ts:331–345` reads stock_settled then appends sale movements before :352–362 writes the flag. Two requests can both see false; stock_movements has no unique transition key (`20260724110000_commerce.sql:76–90`) and `recordMovement` always inserts (`lib/admin/inventory.ts:95–103`). Even a single partial failure before the flag leaves retry able to debit again. Payment/cancel racing is also possible: cancel reads state and releases/restores before independent status update (`orders.ts:458–474`). `setStatus` does not condition update on original state and discards DB error (:385–394), so stale actions can overwrite a newer state or report success without persistence. Atomic single-pool reserve RPC is correct (:111–118 of commerce SQL), but it is not an order-level transaction. Use locked/conditional transactional transition RPCs, movement identities per transition/line, checked database results, and transactional audit/outbox. Validate two simultaneous confirm-payment calls; confirm vs expire; refund retry; rollback mid-basket; assert exact ledger delta and legal final status. Effort 4–7 days, shared with #2.

4. **P1 — Four mutation crons fail open if secret is missing.** `app/api/cron/email-outbox/route.ts:14–20`, `payment-ops/route.ts:20–26`, `abandoned-carts/route.ts:9–15`, `lifecycle/route.ts:23–29`: auth is conditional on secret truthiness, so absent configuration exposes sending/expiry/completion operations to any GET. Daily brief already has correct 503 missing-secret / 401 mismatch guard (`daily-brief/route.ts:34–43`). Production secret presence unverified. Share a fail-closed guard across all cron endpoints and validate required production config at startup. Tests: missing secret 503, absent/wrong bearer 401 and zero work calls, correct bearer succeeds. Effort 0.5 day.

5. **P1/P2 — Outbox lacks durable claims and retry policy; success metrics ignore write failures.** `lib/email/sender.ts:69–90` immediate sender loads any row without claim; :94–118 drain selects oldest queued/failed rows, sends, then updates status. Neither sender claims/excludes rows atomically or passes provider idempotency. Race across immediate/drain or overlapping schedules can duplicate mail; successful provider delivery + failed status write causes re-send. Reads/writes ignore Supabase error responses; failed poison rows stay oldest indefinitely and can starve later rows once batch fills. Retired templates are returned as failure (:48–49) and therefore retried forever. Queue is actually awaited through provider delivery (`lib/admin/email.ts:63–65`), adding email/render/database latency to checkout despite “non-blocking” comment. Add transactional enqueue, background worker claim/lease, stable provider idempotency key, attempt count/next_attempt_at/backoff/dead-letter, cancellation and checked writes. Isolated fake-provider tests: concurrent workers send once, lease recovery after crash, retries don't starve later rows, retired template terminal, checkout latency independent of provider. Effort 3–5 days.

6. **P1/P2 — Public write seams lack abuse controls and verified consent renewal.** `app/api/subscribe/route.ts:18–38` accepts arbitrary valid email and arbitrary source; resets suppression on *all* source rows solely on unauthenticated request. A third party can re-enable marketing for an opted-out address; arbitrary sources also create more records. Public order submission reserves scarce stock with only basic input validation (`checkout/actions.ts:57–65`, :132–189); no application rate limit/challenge or email ownership verification located. Source evidence does not establish absent hosting WAF or actual abuse. Add bounded runtime schemas, allowed sources, email/IP/session rate limits, adaptive bot controls; renew prior opt-out only after confirmation from that mailbox. Keep checkout email UX proportionate. Validate isolated throttling and opt-out ownership cases. Effort 2–4 days.

## Reliability and optimisation foundations

7. **P2 — Marketing suppression only checked when queued, not when retried.** `lib/admin/lifecycle.ts:106–125` applies subscriber suppression/pauses before queueEmail; `sender.ts:45–60,94–106` retries without re-evaluating current suppression. A failed marketing email queued before unsubscribe can be delivered the next drain after opt-out. `api/unsubscribe/route.ts:36–47` and subscribe :30–38 discard database errors and still render success, so failed writes can produce misleading consent status. Check suppression before every marketing dispatch; cancel eligible pending rows when preference changes; preserve transactional sends. Use explicit consent/error state; failures must not be reported as success. Test queue-fail-unsubscribe-drain, paused sequence, DB failure and genuine re-opt-in. Effort 1–2 days.

8. **P2 — Sale eligibility differs between catalog and checkout; successful empty catalog resurrects fallback.** [lib/catalog.ts:215](</Users/shanakajayakody/eastcoastlabs/storefront/lib/catalog.ts:215>) shows only active products, but `lib/checkout.ts:100–104` filters variant.active only, never parent products.status. `lib/admin/products.ts:520–531` updates parent status without disabling variants. Archived/draft stocked product in saved/tampered cart remains buyable. Catalog :236–238 treats a successful empty query as outage and serves stale fallback products, so intentional unpublishing cannot produce an empty store. Shared active-parent/active-variant eligibility in transaction; distinguish empty success, unavailable backend and safe last-known catalog. Validate archive stocked product blocks existing cart and all-hidden catalog stays empty. Effort 1–2 days.

9. **P2 — Catalogue/settings reads are broad/repeated and reviews aggregate in application memory.** `getCatalog` (`lib/catalog.ts:200–216`) fetches all descriptions/images/variants/inventory with default limit 100 and no deterministic DB order, then JS sorts; `getCatalogProduct` :244–246 searches only that capped catalog instead of querying slug. Catalog growth past 100 risks legitimate product 404s and sitemap omissions. PDP calls catalog in metadata and page (`app/(store)/product/[slug]/page.tsx:34,51`), stack lookups can call it per cart stack (`lib/checkout.ts:84–85`, `lib/stacks.ts:49–50,95–96`). `getSettings` is not request-memoized (`lib/settings.ts:80–85`) and is reused by layout/banner/quote/cart/email templates. Supabase fetch may dedupe some GETs, so measure actual network calls rather than assume every call duplicates. `lib/reviews.ts:57–68,100–109,123–134` fetches all review bodies even for counts, recent three, and slug subset aggregates; it also inherits default backend row cap. Use separate summary/detail queries, slug lookups independent of listing limit, stable pagination, request cache and invalidatable data tags; aggregate ratings in SQL. Keep transaction inventory/price validation live. Validate >100-product and >1,000-review synthetic fixtures, query budgets and p95 before/after. Effort 2–4 days.

10. **P2 — Admin source-of-truth drift for bundle pricing/settings updates.** `lib/stacks.ts:61–77` calculates bundle price from getPricing's static [data/price-table.json](</Users/shanakajayakody/eastcoastlabs/storefront/data/price-table.json>) ([lib/pricing.ts:12](</Users/shanakajayakody/eastcoastlabs/storefront/lib/pricing.ts:12>)), while normal product tiers use DB. Checkout then accepts that server-derived static bundle price (`lib/checkout.ts:171–181`). Updating components in admin can leave bundle cost/savings unchanged. Derive all paid product/bundle/accessory price rules from one versioned DB snapshot; keep static files only as display fallback when safe. Settings save writes many keys sequentially (`app/admin/(dashboard)/settings/actions.ts:68–91`), permitting partial updated payment/shipping config on failure; use one batch upsert transaction and invalidate once. Validate component reprice reflected in bundle quote/order and settings save rollback. Effort 2–3 days, coordinate admin/frontend owners.

## Strengths and uncertainty safeguards

- requireAdmin validates real Supabase user AND active allowlist (`lib/admin/auth.ts:28–51`); request render cache already present. Checked admin action exports and print/export/preview seams explicitly guard access; arithmetic suggestTierPrices is public but has no data access, not an auth vulnerability.
- Anonymous callers cannot directly write sensitive tables according to checked-in RLS grants; inventory reserve functions are SECURITY INVOKER, not SECURITY DEFINER, so default function EXECUTE alone is not a bypass of underlying RLS. Did not allege exposed service-role key: common module lacks server-only enforcement but no evidence of secret bundling.
- Database uses unique outbox enqueue keys and webhook event keys; these correctly prevent duplicate queue rows/events but do not guarantee one external send.
- Resend webhook signature verification uses timestamp tolerance + constant-time comparison and fails closed in production if secret unset (`lib/email/webhook-verify.ts:32–38,46–71`). Issue is persistence/ACK reliability, not forged signature bypass.
- Useful existing indexes cover order status/date, email, items/order, inventory PK, outbox status/date and cron job/date. Propose additional workload indexes only after EXPLAIN on realistic staging data; no live query plans were measured.
- Header/role/MFA/session settings, backups/PITR, production WAF, dependency risk and live DB grants were not independently verified. They are follow-up validation items, not confirmed vulnerabilities.
