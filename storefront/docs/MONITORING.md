# Operational monitoring and release budgets

`GET /api/operations/health` with `Authorization: Bearer <CRON_SECRET>` is a read-only monitor target. It returns only job names, freshness states and aggregate delivery counts. It does not run sweeps, send messages, expose recipients, or include raw database errors. Missing auth fails closed. Responses are private/no-store.

`.github/workflows/operations-health.yml` provides a best-effort GitHub Actions check every five minutes, with a manual **Run workflow** option. It runs `node storefront/scripts/probe-operations.mjs` using Node 22 without installing application dependencies. Add the repository Actions secret `CRON_SECRET` with the same value used by the production health endpoint. Do not paste the secret into a URL, command argument or workflow file. The script sends it only in the operations request's Authorization header.

The workflow checks `https://www.eastcoastlabs.com.au/` for HTTP 200 separately from `https://www.eastcoastlabs.com.au/api/operations/health`. Each request has a 15-second timeout, including the health response body. Redirects are not followed, so an authenticated request cannot forward its secret to another destination. The operations probe requires HTTP 200, `ok: true`, healthy job states and zero dead/overdue deliveries. A 503 indicates a missing/failed/overdue scheduler, dead email, delivery more than two hours past its next attempt, or a failed health read. The admin Automation workspace supplies authorised detail.

A failed probe is rechecked once after 30 seconds within the same workflow run. Two failures produce a failed Actions run; a successful recheck passes that probe. A missing `CRON_SECRET` fails configuration immediately while the public check still runs. Logs report **Public availability** and **Operations health** independently, using fixed summaries and HTTP status codes; they never print response bodies, raw errors or credentials. The probes never invoke cron/sweep routes or send emails.

GitHub schedules can be delayed or dropped and run from the default branch. This workflow is a best-effort signal, not a guaranteed external pager or an availability measurement with a fixed sampling interval. It maintains no incident state across runs and does not implement two-success recovery alerts. For a separate monitoring service, retain the target configuration of checks every five minutes, failure after two consecutive failures, and recovery after two successes; route alerts to an actual operator destination. No external monitoring account or pager is provisioned by this workflow. See [GitHub schedule limitations](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Failed monitoring and existing sweep runs appear in GitHub Actions. Actual email/web notification delivery depends on the operator's GitHub Actions notification settings and scheduled-workflow subscription/actor. It has not been verified by these code changes. After release, manually run **Production health monitoring**, inspect both probe results, then have the account owner verify notification delivery and confirm scheduled runs are appearing. See [GitHub workflow notifications](https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs). Keep failed runs visible until their cause is resolved; an operations failure alone does not mean the storefront is unavailable.

`npx vitest run tests/operations-probe.test.ts` exercises the probes against local HTTP servers with synthetic credentials, including retry/recovery, job and queue failures, redirects, malformed responses, missing configuration and a stalled response body. No production services are contacted by those tests.

`config/performance-budgets.json` defines initial release targets, not measured service-level results. The availability target is 99.9% over 30 days (43.2 minutes error budget); investigate a 14.4× burn sustained for one hour or 6× for six hours. Track public synthetic HTTP checks separately from operations-health failures so a delayed internal job does not get reported as an unavailable storefront. Field vitals need 28-day p75 measurements, segmented by device; current hooks can send LCP/INP/CLS to the configured analytics service. Quote/admin p95 query targets require at least 100 observations; exclude contact fields, cart tokens, IDs and query values from logs.

`npm run check:budgets` follows the built app manifest and includes each page plus every parent layout. It counts each JavaScript chunk once and sums its gzip size, in decimal kB. This is intentionally an explicit reproducible metric and differs from Next's printed route estimate. Initial baseline at 8686367: home130.4, shop132.9, product132.1, checkout133.4, product editor159.2, order detail147.0 kB. Public limits allow roughly 5% headroom, with explicit space for checkout recovery; admin order detail allows the new financial/packing workflow. Budget failures require code inspection and a documented review of any limit increase.

`npm run test:headers` starts an owned loopback server from the production build, explicitly blanks application/provider credentials, checks private response headers and expected statuses on nine synthetic private-route requests, and shuts the server down. It follows no redirects and logs no response bodies. Run with `NEXT_DIST_DIR` matching your build output when using a separate verification directory.

CI runs the entire SQL chain in PostgreSQL17, separate-session checkout/stock/refund/settlement races, a pg_dump/pg_restore round trip with all public/storage table digests and public-role denial, and browser fixtures at 320/390/1280px. All databases and provider actions are synthetic. This proves the procedure locally; it does not prove that a production backup has been taken or that externally configured monitors deliver alerts.

Sources: [PostgreSQL backup/restore](https://www.postgresql.org/docs/current/backup-dump.html), [Playwright acceptance and CI setup](https://playwright.dev/docs/intro).
