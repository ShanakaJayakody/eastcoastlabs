# Guarded email operations

The admin automation page exposes cancellation, bounded retry, and provider reconciliation. Every action requires an authenticated, allowlisted administrator and an audit reason. The database rechecks current row state under lock. An active delivery lease always blocks operator changes; cancellation cannot recall a provider request. The controls never call the send API or change an outbox ID, recipient, template, payload, frozen message, attempt count, first attempt time, or provider dedupe key.

Cancellation is available only before any possible provider contact. Retry accepts failed/dead work or an expired lease, requires elapsed backoff, fewer than six claims and an original attempt less than 23 hours old, and rechecks current consent/order eligibility. A message with no provider attempt may retry within that same claim budget. Attempted messages additionally require the frozen sender, subject and HTML. No budget/time reset is offered. Suppressed or revoked cart recovery cannot be restored by retrying an old message.

The sender now freezes the sender address and `ecl_outbox_id` identity tag along with subject and HTML through `prepare_email_delivery_v2`. Retries send exactly that request with `ecl-outbox/<outbox-id>`. Historical attempted rows without a recorded sender or identity tag remain unresolved; the code never assumes today's sender was used earlier. New unattempted rows freeze the current configured sender before authorization.

For a recorded provider ID, reconciliation requires that exact ID and an email event already linked to that outbox and recipient. For the accepted-but-ID-write-lost case, an operator supplies a provider ID and the server uses the read-only [Resend retrieve email API](https://resend.com/docs/api-reference/emails/retrieve-email). It requires the exact frozen outbox ID tag and the same sole recipient, sender, subject and original HTML, no CC/BCC, an accepted send state, and a provider creation time consistent with the attempted send. Old provider messages without that tag, missing content or any mismatch leaves the row unresolved. This is strict equality; transformed or unavailable provider content cannot be guessed. Original text is not sent by this sender; provider-generated text is not treated as proof of an independently authored text body.

After verification, `admin_reconcile_email` compares the frozen snapshot (including tag) and lease/status again in the transaction, rejects an ID attached to another row, attaches exact matching webhook records, and audits the provider ID, operator and reason. It marks provider acceptance as `sent`, matching existing outbox semantics; delivery/bounce/complaint events remain separately visible in customer history. It never resends. A reconciled bounce is still a bounce.

An unresolved historical row needs investigation in the provider account and the customer delivery history. Do not create a new outbox identity merely to bypass an exhausted dedupe window. These controls do not revoke recovery credentials: use the existing customer recovery stop or suppression controls for that separate purpose.
