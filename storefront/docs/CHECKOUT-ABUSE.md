# Checkout reservation limits

Public checkout must supply its validated, stable UUID idempotency key. In `commerce_create_order`, a committed replay is returned before rate checks; retrying an uncertain successful checkout therefore works even when the customer has reached a limit. A different payload reusing the key remains rejected.

For a new public checkout, the database takes a transaction advisory lock on the normalized email before counting and creating. At most **five pending orders with a future payment expiry** and **ten orders created within the preceding 60 minutes** are allowed for that normalized email. Reaching either threshold raises the explicit `CHECKOUT_RATE_LIMIT` error before an order or reservation is inserted. All orders for that address count, including cancelled, paid and admin-created orders in the rolling-hour count. Cancellation/payment/expiry frees a pending slot, but does not erase recent creation history. Expiry frees this rate-limit slot even if the independent stock-release cron has not run yet; actual inventory remains protected by its reservation transaction.

Trusted admin creation without a public idempotency key is not rate limited. Public server actions must continue requiring a valid UUID and must not expose that bypass. Direct commerce RPC execution remains service-role-only. Constants `checkout_pending_limit`, `checkout_hourly_limit` and `checkout_window` are adjacent at the top of the function for staging review. If changed after this migration is deployed, add a new migration replacing the function; do not edit a recorded migration.

Lock order is request UUID → normalized email → new order/product/inventory → discount. Existing-order transitions do not acquire the email lock. Checks execute under that lock so concurrent creates for the same address cannot both consume the final slot. The shared PGlite regression tests cover limit boundaries, normalization, replay, admin bypass, expiry and rolling history; a separate-session PostgreSQL concurrency test remains a staging check.

This is a heuristic against repeated same-address stock reservation, not a complete abuse prevention system. An attacker can rotate email addresses. Production also needs trusted edge/WAF limits by source IP and suitable session/challenge controls, with thresholds verified against real customer traffic. Do not trust a browser-submitted IP or arbitrary forwarded header as an abuse identity. No external WAF or live production configuration was changed here.
